# 云同步首版设计

自建版在设备间同步文本、图片与单文件。客户端把新增和跨端删除统一保存为本地变更，再按产生顺序通过 HTTPS 上传。在线时尽快发送，断网时保存在 SQLite，恢复后分批补传。云端按提交顺序记录变更，客户端通过 SSE 得知有变更，再按游标拉取。收到同一批云端动作后，各设备会得到相同的同步状态。设备可以按各自的保留数量清理本机历史。

服务端采用 Spring Boot 和 MySQL，自建部署使用部署令牌。商业版复用协议，以服务端根据登录凭据确定的账号为同步范围。图片和文件在文本流程验收后接入，文件本体使用 OSS。

## 两种变更和三个标识

| 项目 | 用途 |
| --- | --- |
| `upsert` | 新增或重新复制内容。按 `content_key` 创建或恢复记录，已存在时仍只保留一条。 |
| `delete` | 用户显式发起跨端删除。按 `content_key` 删除记录，目标已不存在时照常确认。 |
| `content_key` | 标识相同内容。客户端和服务端都按它去重，各自的数据库主键只在本库使用。 |
| `operation_id` | 标识一次动作，在本机入队时生成。请求超时或响应丢失后使用同一个 ID 重传。用户重新复制会生成新的 ID。 |
| `sync_seq` | 云端为首次接收的动作分配的 `BIGINT` 序号。客户端按此顺序回放，并保存最后处理完的序号。同步时间用于展示和排查。 |

同一台设备按本地操作顺序上传。不同设备之间按云端提交顺序执行，最后提交的动作决定该内容在同步范围内是存在还是删除。举例来说，A 离线时复制「123」，B 在线删除「123」，随后 A 首次成功上传这次复制，「123」会重新出现。如果 A 的旧动作已经在云端提交，即使 A 当时未收到确认，服务端也会返回原确认和原序号，后面的删除仍然有效。

## 本机 SQLite

| 表或配置 | 内容 |
| --- | --- |
| `clip_record`、`clip_record_resource` | 单机核心的现有记录表和资源表。各版本共用同一套本地采集、查询和物理删除逻辑。 |
| `clip_sync_record` | 自建版上传动作表。`upload_status=0` 表示待上传，按自增 `id` 发送，`operation_id` 唯一。新增动作入队时通过 `record_id` 关联本机记录，确认后标记 `upload_status=1`，随本机记录删除。删除动作使用 `content_key`，收到确认后清理。 |
| `clip_sync_state` | 自建版使用一行保存 `pull_cursor` 和附件开关，首次登记历史与创建状态行同事务提交。 |

本地业务变更和入队使用同一个 SQLite 事务。上传时通过 `record_id` 从 `clip_record` 读取文本密文，或从 `clip_record_resource` 读取附件信息和受管副本。附件描述在发送时生成并加密。副本缺失或内容校验失败时，记录日志并移除对应的新增动作。后续动作继续按顺序处理。

启用部署同步的自建版中，手动删除记录会在同一事务内写入 `delete` 动作并删除本机记录。外键级联只清理该记录的新增动作。`delete` 的 `record_id` 为空，通过 `content_key` 标识目标。断网或重启后使用同一个 `operation_id` 补传，收到该批次完整的上传确认后才清理。补拉和游标更新可以独立完成。本机容量淘汰只清理当前设备的历史。应用远端动作时，复用本地保存或清理逻辑，并跳过入队，避免下载回来的变更再次上传。

## 云端 MySQL

| 表 | 内容 |
| --- | --- |
| 云端记录表 `clip_record` | `id`、`content_key`、`type`、`content`、`created`、`updated`、`del_flag`。自建版按 `content_key` 唯一，商业版按 `(user_id, content_key)` 唯一。当前记录查询只返回仍存在的内容。 |
| 云端变更表 `clip_sync_change` | 追加保存 `id`、`operation_id`、`content_key`、`action`、`record_id`、`client_created`、`request_hash` 及基础字段。自增 `id` 直接映射为协议 `sync_seq`，`created` 映射为 `committed_at`。`upsert` 关联云端内部的内容记录，`delete` 只需要内容键。按同步范围和序号分页，`operation_id` 的唯一约束覆盖该同步范围，用这张表直接查重试确认。 |

云端内容按内容键保存一份。文本对同一个 `content_key` 的原文固定，因此历史 `upsert` 可以引用同一份存储内容。云端删除更新当前状态并追加 `delete`，供离线设备回放。在保留旧增删历史期间，仍被 `upsert` 引用的正文也要保留，否则旧动作无法回放。待定义快照和旧游标恢复后，再一起设计历史、重试凭据及无引用内容的回收。附件接入后按同样规则管理 OSS 对象的保留期限。

单实例部署首期串行执行同步写入，锁覆盖序号分配到 MySQL 事务提交的整个过程。云端记录更新和变更日志一起提交，提交成功才返回确认并安排 SSE 通知。序号允许有空档，较大序号可查询后，较小序号的动作必须已提交或确定不会再出现。客户端据此安全推进游标。

## 上传、补拉和失败恢复

1. **先入队，再发送。** 本机在线和离线都走同一条写入流程。在线时唤醒上传任务，重启或恢复网络后扫描 SQLite 队列。每个同步范围只允许一个发送任务。它按本地 `id` 从小到大组批，上一批获得确认后再发下一批。积压多时连续分批处理，每批限制条数和大小。
2. **确认和重试。** 首期每批按请求内的顺序在同一个 MySQL 事务里处理。已提交的 `operation_id` 返回原来对应的序号，其余动作依序提交。服务端提交前出错时整批回滚。客户端按确认更新新增状态或清理删除动作，超时和临时错误退避重试。无效数据导致批次持续失败时保留队列并显示失败，避免跳过早期动作后继续提交后续动作。
3. **SSE 唤醒补拉。** 云端每 300～500 毫秒合并同一范围内的提交，通知在线设备最新序号。自建版按部署通知，商业版按账号通知。客户端仅用通知调度补拉，从本机游标开始经 HTTPS 查询，按 `sync_seq` 升序处理。本机上传和补拉可以并行，每个范围只运行一个补拉任务。补拉期间收到的新通知合并处理。
4. **落库和游标一起提交。** 每页动作按序应用，处理完后把该页最后一个序号和本地写入放进同一个 SQLite 事务。空页保留原游标。失败从原游标重拉。本机发出的动作也按云端顺序回放。补拉遇到与本机待上传新增对应的删除时，从原游标重试这一页，等新增确认或从队列清理后再回放。
5. **启用和重连。** 首次开启时把符合条件的原有本机历史登记为待发送 `upsert`，每个同步范围只执行一次，同时从游标 `0` 开始拉取。重连时唤醒发送和补拉，也可以在同一个 HTTPS 请求里附带一批动作和当前游标，分别返回上传确认和一页云端变更。频繁重连合并触发，每轮限制页数或耗时，积压较多时按已提交游标继续。在线期间保留低频补拉，弥补云端提交后通知未发出的情况。

自建版使用持续运行的 MySQL 变更日志。本机只有一条补拉游标和一份待传队列。启动及 SSE 重连之后从最后一次落库的游标继续。更换服务地址或数据库时，可在关闭客户端后按需调整 `clip_sync_state.pull_cursor`。

## 客户端监听与补拉职责

把补拉作为同步会话内的独立任务。各处通过一个 `request_pull()` 入口发出唤醒信号，补拉任务顺序处理这些信号。用一个容量为 1 的 Tokio 异步通道即可合并触发。通道只传递唤醒信号，待上传动作仍保存在 SQLite。

| 组件 | 放置位置和职责 |
| --- | --- |
| SSE 监听器 | `clip-sync-client`。管理连接、读取通知、处理断线重连。连接建立或收到变更通知时调用 `request_pull()`。通知里的序号可用于排查同步延迟。 |
| 补拉任务 | `clip-sync-client`。每个同步会话启动一个任务。读取已提交游标，调用 HTTPS 分页接口，按顺序把每一页交给本机同步仓储。补拉的限频、批次上限和重试统一放在这里。 |
| 本机同步仓储 | `selfhost-app-core`。执行增删回放和游标更新，整页在一个 SQLite 事务中提交。沿用单机的记录和资源处理，并为远端回放跳过待上传入队。 |
| 同步会话 | 由自建应用核心组装，桌面层通过 `AppContext` 持有会话。启动时注册 SSE 监听、低频兜底定时器及上传唤醒入口，关闭同步或切换范围时停止旧任务，再开启新会话。 |

各入口只表达需要做什么，具体的请求、事务和重试由对应任务执行。

| 触发时机 | 调度动作 |
| --- | --- |
| 首次启用同步 | 完成本机历史的首次入队，唤醒上传和补拉。 |
| SSE 首次连接或重连成功 | 请求一次补拉，并唤醒待上传队列。 |
| SSE 收到云端变更通知 | 请求补拉。 |
| 网络从不可用恢复，或低频兜底定时器到期 | 请求补拉。恢复网络时也唤醒上传，SSE 重连与此处的补拉请求会合并。 |
| 本机新增或显式跨端删除提交成功 | 唤醒上传任务。若上传响应也包含拉取页，该页交由同一个补拉任务处理。只有响应对应的起始游标与当前游标一致时才应用，否则从当前游标重新拉取。 |

运行时，补拉任务开始前取走通道内的信号。拉取期间来了十次通知，只留一个待处理信号。当前轮结束后，根据已落库的游标执行下一轮，并遵守最短启动间隔。达到每轮的页数或耗时上限时，若服务端仍有下一页，补拉任务给自己排一次后续唤醒。网络失败时按退避时间继续，收到新通知时仍遵守这个时间。游标由仓储成功提交后推进，上传确认和 SSE 通知都只用于各自的调度或确认。

实现时可单独测试触发合并、按游标分页和仓储事务。用测试替身驱动补拉任务，就能验证拉取过程中收到通知、某页落库失败、以及切换会话后旧结果不会写入新范围等场景。

## 首期验收场景

| 场景 | 预期结果 |
| --- | --- |
| A 在线复制文本，B 收到 SSE | B 从本机游标开始拉取，落库后推进游标。 |
| A 断网并退出，重启后恢复联网 | A 从持久化队列恢复未确认的动作，按本地顺序上传。 |
| A 离线先删「123」，随后复制「123」 | 云端按顺序记录 `delete`、`upsert`，其他设备回放后存在「123」。 |
| A 的新增已提交但响应丢失，B 随后删除 | A 重试得到原序号，云端只执行 B 的删除，记录保持已删除。 |
| A 的离线新增在 B 的在线删除后才首次提交 | 新增获得更大的序号，各设备回放后恢复该记录。 |
| SSE 丢失或连续重连 | 重连触发合并补拉，漏掉的变更仍可按序号取回。 |
| 本机超限淘汰或仅删除本机历史 | 本机正常释放记录和缓存，云端保持原状态。 |
| 补拉落库失败，或者并行产生新的本机操作 | 补拉从旧游标重试，新操作留在本机队列，最终按云端提交顺序收敛。 |
| 一轮补拉过程中收到多次 SSE 通知 | 同一会话始终只有一个补拉任务，当前轮结束后按新游标合并检查一次。 |

## 客户端首期实现

自建包的 `cloud_sync.enabled` 默认关闭。需要同步时在打包配置中设为 `true`，填写部署 HTTPS 地址和令牌。同一部署的设备使用同一个数据加密密钥。客户端设置中的云同步开关立即生效，重启时沿用本机选择。关闭同步后保留已排队的操作和补拉游标，恢复时继续处理。首次读取 `/limits` 成功后，客户端登记符合条件的本机历史。已有队列在离线启动时可以继续入队。

首版开发阶段，客户端按当前结构初始化同步表。表结构变更后使用新开发库。使用同一份当前结构的库重启客户端时，会继续读取已有游标和待传动作。

所有 V2 端点使用 `Authorization: Bearer <deployment_token>`，JSON 端点的成功响应直接返回协议数据。客户端和服务端一起升级。

| 方法和相对路径 | 契约 |
| --- | --- |
| `GET sync/limits` | 返回大小限制、条数配额和 OSS 附件开关。 |
| `POST sync/operations` | JSON 请求携带按本地顺序排列的 `operations`。响应包含 `acknowledgements`，每项确认带 `operation_id`、`sync_seq`。 |
| `GET sync/changes` | 查询参数为 `after`、`limit`。响应包含升序 `changes` 及 `has_more`。 |
| `GET sync/events` | 连接返回 `text/event-stream`，变更通知用带 `data:` 的 `event: changed`。建议服务端每 15 秒发送注释心跳，客户端 45 秒没有收到数据时重连。 |

上传和补拉各自分批，首版采用独立请求。每批最多 100 条，单条文本原文最多 5 MiB，上传批次最多携带 8 MiB 密文和 8 MiB 附件。超出同步上限的文本仍可在本机保存。补拉也建议按同样的条数和密文大小预算分页。客户端在每页的本地事务提交后推进游标，远端回放更新本机搜索和列表。设置中会显示同步、等待重试和异常状态。手动删除在本机事务提交后即完成登记，离线或关闭同步时，等恢复连接且同步开启后再发送。


## 云端首期落地约定（2026-11-24）

服务端独立工程为同级目录 `clip-pal-sync`，使用单模块 Spring Boot。两张业务表保持旧 Java 基础字段 `id`、`created`、`updated`、`del_flag`，主键均为自增 BIGINT。记录表的删除改变最终状态；删除动作本身仍是一条有效日志，其 `del_flag` 固定为0。动作表不保存正文，按云端 `record_id` 关联第一份已验证密文。

数据库手动执行服务端 `sql/init.sql` 创建，不使用 Flyway，不在应用启动时建表。真实内容密钥保存在服务端部署配置中。自建版不创建账号、设备进度或元数据业务表。

首版限定一个服务端进程写一个自建库。`SyncService` 的进程锁包围完整 `TransactionTemplate`，从事务开始到提交完成才释放，保证动作自增 ID 的可见顺序。事务提交后再发布内部事件，统一通过 `requestNotify()` 合并SSE通知。多实例写入需要后续增加提交顺序协调，不能直接复制部署多个进程。

正文在日志保留期间不物理删除，重复新增只更新最终状态和时间，保留首份验证通过的密文。同一操作 ID 重传时先校验内容，再比较内容键、动作类型和客户端时间的摘要。相同则返回原序号，不同则整批回滚。上传确认不改变客户端补拉游标。

### 图片与单文件

- 自建版默认允许同步最多 5 MiB 的 UTF-8 文本原文、图片或单个普通文件。二进制多选清单按完整内容摘要去重并留在本机。目录、多文件、超限记录和部署未开启的附件类型在卡片上提示原因。
- 客户端向部署服务申请短期签名 URL，直接向私有 OSS 桶上传或下载。云端 `content` 保存加密附件描述，其中包含稳定对象标识、文件名、大小和 SHA-256。新对象在操作 ID 后追加安全的文件后缀，旧对象沿用原标识。签名 URL 每次传输时申请。附件字节由私有桶保管，部署者可读取。
- 附件字节从软件维护的本地副本读取。上行和下行共用两个传输名额，状态显示在对应记录卡片的标题栏。收到云端确认后，在同一 SQLite 事务中将新增动作标记为已上传。重启后从本地库读取确认。下载完成并落库后显示普通卡片。下载失败从已提交的游标重试，整个文件重新传输。补拉下载成功并校验摘要后才提交记录和游标。
- 文件保存到独立备份。默认使用与 `data` 同级的 `resources/files`，设置中可选择其他目录。切换目录后，已有备份继续从原目录读取。
- `GET sync/limits` 返回部署能力，`max_records` 为商业扩展预留。自建版云端条数不限。MySQL 开发库使用服务端的 `sql/init.sql` 初始化。
