# 云同步首版设计

自建版先跑通两台设备的文本同步。客户端把新增和跨端删除统一保存为本地变更，再按产生顺序通过 HTTPS 上传。在线时尽快发送，断网时保存在 SQLite，恢复后分批补传。云端按提交顺序记录变更，客户端通过 SSE 得知有变更，再按游标拉取。收到同一批云端动作后，各设备会得到相同的同步状态。设备可以按各自的保留数量清理本机历史。

服务端采用 Spring Boot 和 MySQL，自建部署使用部署令牌。商业版复用协议，以服务端根据登录凭据确定的账号为同步范围。图片和文件在文本流程验收后接入，文件本体使用 OSS。

## 两种变更和三个标识

| 项目 | 用途 |
| --- | --- |
| `upsert` | 新增或重新复制内容。按 `content_key` 创建或恢复记录，已存在时仍只保留一条。 |
| `delete` | 用户显式发起跨端删除。按 `content_key` 删除记录，目标已不存在时照常确认。 |
| `content_key` | 标识相同内容。客户端和服务端都按它去重，各自的数据库主键只在本库使用。 |
| `operation_id` | 标识一次动作，在本机入队时生成。请求超时或响应丢失后重传同一个 ID 和原数据。用户重新复制会生成新的 ID。 |
| `sync_seq` | 云端为首次接收的动作分配的 `BIGINT` 序号。客户端按此顺序回放，并保存最后处理完的序号。同步时间用于展示和排查。 |

同一台设备按本地操作顺序上传。不同设备之间按云端提交顺序执行，最后提交的动作决定该内容在同步范围内是存在还是删除。举例来说，A 离线时复制「123」，B 在线删除「123」，随后 A 首次成功上传这次复制，「123」会重新出现。如果 A 的旧动作已经在云端提交，即使 A 当时未收到确认，服务端也会返回原确认和原序号，后面的删除仍然有效。

## 本机 SQLite

| 表或配置 | 内容 |
| --- | --- |
| `clip_record`、`clip_record_resource` | 单机核心的现有记录表和资源表。各版本共用同一套本地采集、查询和物理删除逻辑。 |
| `clip_sync_record` | 自建版待发送动作表。保存本机自增 `id`、`operation_id`、`content_key`、动作类型、创建时间及 `upsert` 的加密快照或持久化引用。按自增 `id` 顺序发送，`operation_id` 唯一。 |
| 同步状态 | 自建版独立保存同步范围、云端数据集标识、该范围的 `pull_cursor` 和首次导入状态。 |

本地业务变更和入队使用同一个 SQLite 事务。`record_id` 可以作为可选的本机定位信息。一旦入队，动作及其内容保持固定，直到收到云端确认。记录被删除或淘汰后，此前入队的动作继续按原顺序发送。`delete` 只需内容键和动作元数据。`upsert` 则需要保有当时可上传的内容。文本首期可在入队时保存现有加密格式的密文快照，收到确认后一起清理。这样离线期间先复制后删除，前一条新增也有数据可发。

用户显式跨端删除时，物理删除本机记录和写入 `delete` 动作一起提交。本机容量淘汰和仅删除本机历史继续按本机规则处理。应用远端动作时，复用本地保存或清理逻辑，并跳过入队，避免下载回来的变更再次上传。

## 云端 MySQL

| 表 | 内容 |
| --- | --- |
| 云端记录表 `clip_record` | `id`、`content_key`、类型、内容、`deleted_at`、创建和更新时间。自建版按 `content_key` 唯一，商业版按 `(user_id, content_key)` 唯一。当前记录查询只返回仍存在的内容。 |
| 云端变更表 `clip_sync_change` | 追加保存 `sync_seq`、`operation_id`、`content_key`、动作类型、提交时间。`upsert` 关联云端内部的内容记录，`delete` 只需要内容键。按同步范围和序号分页，`operation_id` 的唯一约束覆盖该同步范围，用这张表直接查重试确认。 |

云端内容按内容键保存一份。文本对同一个 `content_key` 的原文固定，因此历史 `upsert` 可以引用同一份存储内容。云端删除更新当前状态并追加 `delete`，供离线设备回放。在保留旧增删历史期间，仍被 `upsert` 引用的正文也要保留，否则旧动作无法回放。待定义快照和旧游标恢复后，再一起设计历史、重试凭据及无引用内容的回收。附件接入后按同样规则管理 OSS 对象的保留期限。

单实例部署首期串行执行同步写入，锁覆盖序号分配到 MySQL 事务提交的整个过程。云端记录更新和变更日志一起提交，提交成功才返回确认并安排 SSE 通知。序号允许有空档，较大序号可查询后，较小序号的动作必须已提交或确定不会再出现。客户端据此安全推进游标。

## 上传、补拉和失败恢复

1. **先入队，再发送。** 本机在线和离线都走同一条写入流程。在线时唤醒上传任务，重启或恢复网络后扫描 SQLite 队列。每个同步范围只允许一个发送任务。它按本地 `id` 从小到大组批，上一批获得确认后再发下一批。积压多时连续分批处理，每批限制条数和大小。
2. **确认和重试。** 首期每批按请求内的顺序在同一个 MySQL 事务里处理。已提交的 `operation_id` 返回原来对应的序号，其余动作依序提交。服务端提交前出错时整批回滚。客户端收到确认后按 `operation_id` 清理本批，超时和临时错误退避重试。无效数据导致批次持续失败时保留队列并显示失败，避免跳过早期动作后继续提交后续动作。
3. **SSE 唤醒补拉。** 云端每 300～500 毫秒合并同一范围内的提交，通知在线设备最新序号。自建版按部署通知，商业版按账号通知。客户端仅用通知调度补拉，从本机游标开始经 HTTPS 查询，按 `sync_seq` 升序处理。本机上传和补拉可以并行，每个范围只运行一个补拉任务。补拉期间收到的新通知合并处理。
4. **落库和游标一起提交。** 每页动作按序应用，处理完后把该页最后一个序号和本地写入放进同一个 SQLite 事务。空页保留原游标。失败从原游标重拉。本机发出的动作也按云端顺序回放，上传确认仅用于清理待发送队列。若补拉暂时覆盖了本机尚待发送的改动，独立保存的动作仍能上传，最终结果由云端回放恢复。
5. **启用和重连。** 首次开启时把符合条件的原有本机历史登记为待发送 `upsert`，每个同步范围只执行一次，同时从游标 `0` 开始拉取。重连时唤醒发送和补拉，也可以在同一个 HTTPS 请求里附带一批动作和当前游标，分别返回上传确认和一页云端变更。频繁重连合并触发，每轮限制页数或耗时，积压较多时按已提交游标继续。在线期间保留低频补拉，弥补云端提交后通知未发出的情况。

游标和队列绑定创建时的部署或账号及云端数据集。换服务端、切换账号或从旧备份恢复时，按新数据集重新拉取。同步到这个范围的数据应能识别其来源，以便重新拉取时用云端状态重建该范围的同步结果，同时保留仅存本机的内容。旧队列留在原范围，遇到云端数据集换代时暂停发送，避免把旧备份已经丢失的确认当成新的操作。服务端恢复旧备份后应更换数据集标识，避免客户端继续使用已超前的游标。恢复旧队列和回收历史可在首期闭环之后再设计。

## 客户端监听与补拉职责

把补拉作为同步会话内的独立任务。各处通过一个 `request_pull()` 入口发出唤醒信号，补拉任务顺序处理这些信号。用一个容量为 1 的 Tokio 异步通道即可合并触发。通道只传递唤醒信号，待上传动作仍保存在 SQLite。

| 组件 | 放置位置和职责 |
| --- | --- |
| SSE 监听器 | `clip-sync-client`。管理连接、读取通知、处理断线重连。连接建立或收到变更通知时调用 `request_pull()`。通知里的序号可用于排查同步延迟。 |
| 补拉任务 | `clip-sync-client`。每个同步会话启动一个任务。读取已提交游标，调用 HTTPS 分页接口，按顺序把每一页交给本机同步仓储。补拉的限频、批次上限和重试统一放在这里。 |
| 本机同步仓储 | `selfhost-app-core`。执行增删回放和游标更新，整页在一个 SQLite 事务中提交。沿用单机的记录和资源处理，并为远端回放跳过待上传入队。 |
| 同步会话 | 由自建应用核心组装，桌面层通过 `AppContext` 持有会话。启动时注册 SSE 监听、低频兜底定时器及上传唤醒入口，关闭同步或切换范围时停止旧任务，再开启新会话。 |

各入口只表达需要做什么，具体的请求、事务和重试由对应任务执行。

| 触发时机 | 调度动作 |
| --- | --- |
| 首次启用同步 | 完成本机历史的首次入队，唤醒上传和补拉。 |
| SSE 首次连接或重连成功 | 请求一次补拉，并唤醒待上传队列。 |
| SSE 收到云端变更通知 | 请求补拉。 |
| 网络从不可用恢复，或低频兜底定时器到期 | 请求补拉。恢复网络时也唤醒上传，SSE 重连与此处的补拉请求会合并。 |
| 本机新增或显式跨端删除提交成功 | 唤醒上传任务。若上传响应也包含拉取页，该页交由同一个补拉任务处理。只有响应对应的起始游标与当前游标一致时才应用，否则从当前游标重新拉取。 |

运行时，补拉任务开始前取走通道内的信号。拉取期间来了十次通知，只留一个待处理信号。当前轮结束后，根据已落库的游标执行下一轮，并遵守最短启动间隔。达到每轮的页数或耗时上限时，若服务端仍有下一页，补拉任务给自己排一次后续唤醒。网络失败时按退避时间继续，收到新通知时仍遵守这个时间。游标由仓储成功提交后推进，上传确认和 SSE 通知都只用于各自的调度或确认。

实现时可单独测试触发合并、按游标分页和仓储事务。用测试替身驱动补拉任务，就能验证拉取过程中收到通知、某页落库失败、以及切换会话后旧结果不会写入新范围等场景。

## 首期验收场景

| 场景 | 预期结果 |
| --- | --- |
| A 在线复制文本，B 收到 SSE | B 从本机游标开始拉取，落库后推进游标。 |
| A 断网并退出，重启后恢复联网 | A 从持久化队列恢复未确认的动作，按本地顺序上传。 |
| A 离线先删「123」，随后复制「123」 | 云端按顺序记录 `delete`、`upsert`，其他设备回放后存在「123」。 |
| A 的新增已提交但响应丢失，B 随后删除 | A 重试得到原序号，云端只执行 B 的删除，记录保持已删除。 |
| A 的离线新增在 B 的在线删除后才首次提交 | 新增获得更大的序号，各设备回放后恢复该记录。 |
| SSE 丢失或连续重连 | 重连触发合并补拉，漏掉的变更仍可按序号取回。 |
| 本机超限淘汰或仅删除本机历史 | 本机正常释放记录和缓存，云端保持原状态。 |
| 补拉落库失败，或者并行产生新的本机操作 | 补拉从旧游标重试，新操作留在本机队列，最终按云端提交顺序收敛。 |
| 一轮补拉过程中收到多次 SSE 通知 | 同一会话始终只有一个补拉任务，当前轮结束后按新游标合并检查一次。 |

## 客户端首期实现

自建包的 `cloud_sync.enabled` 默认关闭。部署者确认需要同步已有文本后，在打包配置中显式设为 `true`，并配置部署 HTTPS 地址和令牌。同一部署的设备使用同一个数据加密密钥。首次握手验证服务端范围后，客户端才登记并传输现有文本。已完成绑定的客户端可以在离线启动时继续追加到原队列。服务器换代时，客户端暂停旧范围的传输并保留队列，重新绑定及恢复旧数据由后续流程处理。

自建 SQLite 实际使用 `clip_sync_scope` 保存部署地址、服务端范围、数据集和游标。绑定的写入与首次历史登记在一个事务内完成。待确认数据保存在 `clip_sync_record`，由本机范围 ID 关联。 `clip_sync_origin` 按本机记录 ID 记录同步来源，用于隔离不同部署的历史，本机删除时级联移除来源标记。客户端允许切换到另一部署地址并使用独立的游标和队列。发现同一地址的数据集或身份变化时保留原绑定并暂停传输。

所有 V2 端点使用 `Authorization: Bearer <deployment_token>`，JSON 端点的成功响应直接返回下表的数据。服务端必须在提交动作或返回变更前确认请求携带的范围和数据集匹配当前凭据及当前数据集，范围标识本身不授予权限。

| 方法和相对路径 | 契约 |
| --- | --- |
| `GET sync/v2/scope` | 返回 `scope_id` 和 `dataset_id`。客户端在启动传输前核对已有绑定。 |
| `POST sync/v2/operations` | JSON 请求携带 `scope` 和按本地顺序排列的 `operations`。响应包含 `scope` 和 `acknowledgements`，每项确认带 `operation_id`、`sync_seq`。 |
| `GET sync/v2/changes` | 查询参数为 `scope_id`、`dataset_id`、`after`、`limit`。响应包含 `scope`、升序 `changes` 及 `has_more`。 |
| `GET sync/v2/events` | 查询参数为 `scope_id`、`dataset_id`。连接返回 `text/event-stream`，变更通知用带 `data:` 的 `event: changed`。建议服务端每 15 秒发送注释心跳，客户端 45 秒没有收到数据时重连。 |

上传和补拉各自分批，首版采用独立请求。每批最多 100 条，单条文本密文最多 4 MiB，上传批次最多携带 8 MiB 密文。超出同步上限的文本仍可在本机保存。补拉也建议按同样的条数和密文大小预算分页。客户端在每页的本地事务提交后推进游标，远端回放更新本机搜索和列表。设置中会显示同步、等待重试和异常状态。文本删除确认框提供本机删除与跨端删除，跨端删除在本机事务提交后即完成登记，离线时等待恢复连接再发送。
